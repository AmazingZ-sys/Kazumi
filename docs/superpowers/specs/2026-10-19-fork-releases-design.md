# Fork releases and updates

The fork `AmazingZ-sys/Kazumi` builds Android APK, unsigned iOS IPA, macOS DMG, and Windows packages from its own source. New Windows builds use the fork's persistent self-signed Authenticode certificate for `kazumi.exe` and the completed EXE installer, producing both the installer and portable ZIP from one Flutter build. On 2026-10-19, [run 39227772221](https://github.com/AmazingZ-sys/Kazumi/actions/runs/39227772221) at `ac309d0e974a966ccf39042184529c7afc78c1ce` passed all four platform builds, real Windows signature tests, final installer and ZIP executable verification, and temporary trust cleanup. Downloaded Windows artifacts also passed local `osslsigncode 2.14` verification against the committed public certificate. These are Actions artifacts; no new tag or Release was published. Branch pushes produce downloadable Actions artifacts; numeric version tags publish a stable GitHub Release in this fork after tests and all platform builds pass. MSIX publication and SignPath integration remain excluded. Self-signing does not provide public CA trust or guarantee the absence of Windows security prompts. See the [Windows self-signing design](2026-10-19-windows-self-signing-design.md).

The first fork release is `2.3.12+20312`, based on upstream 2.3.9. Its historical Windows ZIP remains unsigned; signing changes apply to new builds and do not replace that release's assets. The initial `2.3.10` and `2.3.11` tags encountered CI setup and Windows CLI compatibility failures and were retained without published releases. The application reads only this fork's latest stable GitHub Release, chooses assets that actually exist, defaults to GitHub downloads, and never falls back to the upstream update mirror. Missing releases mean there is no update; network failures remain visible. SHA256 verification stays mandatory. Windows updates keep selecting the existing portable ZIP filename. iOS opens the fork release page for re-signing/sideloading.

Android and new Windows builds use separate persistent fork signing keys, authorized by the user. Private signing files stay outside Git and are supplied through repository Actions secrets. The Windows signing identity is backed up outside the repository under `~/.local/share/kazumi/windows-signing`; only its public certificate and fingerprint enter Git. Builds keep their platform filename identifiers so the updater can select the correct APK/DMG/ZIP. The public release notes clearly state Windows self-signed trust and iOS/macOS signature limitations.

Validation covers fork release requests, 404, asset selection and source handling, existing Flutter tests/analyzer, packaging tests, workflow structure, and actual cloud builds. New release checksums require five package assets: APK, IPA, DMG, Windows installer and Windows ZIP. Windows verification checks both the installer and ZIP's executable against the pinned public certificate, with temporary hosted-runner trust cleaned afterward. A manual `platform=windows` run can verify Windows alone; tag publication still requires all platforms. A new release is complete only after all five downloadable packages are published and the GitHub release response matches the updater's expectations.
